# 本地权重迁移 · 设计文档

> 2026-09-03 · 状态：设计定稿，待施工
> 目标一句话：**同一份权重文件，全机只下载一次、只占一份盘**。

---

## 1. 问题

面板当前获取权重的唯一手段是「从 HF 下载」。但真实使用里，同一份文件常常已经躺在本机：

- 用户用别的工具（如 bash 前身 `llama-launcher`）下过一份，想迁进来，不再用旧工具
- 同一个文件被两个 HF 仓库分别提供（典型是 mmproj，`unsloth` 与 `bartowski` 的同一份视觉投影文件），
  两个档案各下一次，几 GB 白占
- 用户手动 `wget` 到 models 目录某处，面板不认识它

现状下这些情形要么重下一遍，要么用户自己在宿主机上敲命令搬运。本设计把「本地已经有了」变成
下载流程里的一等公民。

## 2. 现状盘点（调研结论）

**已有的半套**——档案详情页其实已经在做全盘扫描：

| 现有件 | 位置 | 能做 | 差在哪 |
|---|---|---|---|
| stray 识别 | `lib/repo-files-scan.ts:56` | 每次进档案页全盘扫，找出「档案目录外、basename 相同且 size 精确等于远端声明」的文件，标「在别处」 | 被动展示；**显式排除了在任何档案目录内的文件**（`:63`），而那正是「两个仓库同一份文件」的情形 |
| 归位按钮 | `repo-detail-view.tsx:336` | 行内一键 `POST /files/move` 挪进档案目录 | 要逐行手点；stray 行**不可勾选下载**（`repo-files-view.ts:273` `isSelectable` 只放行 absent/partial），点「下载选中项」轮不到它 |
| 入队跳过 | `download/manager.ts:550-562` | 目标路径已存在且 size 等于期望 → 计入 `skipped` 不下载 | 只看目标路径这一个位置，只比 size |
| 物理移动 | `fileMove.ts:77` + `files/move` | 分片组整组搬、事务内重写全部引用、`file_meta.path` 跟迁，**显式放行「移进档案目录」**（`filesApi.ts:552`） | 只有 `renameSync`，无跨盘兜底（EXDEV 会变成没有错误码的裸 500） |
| 引用计数 | `filesApi.ts:buildRefMap` | 每个文件带 `refs`，`refs===0` 即游离 | 接口不做筛选，UI 只有一个被动的「未被引用」chip（`files-table.tsx:796`） |
| 内容指纹 | `core/fingerprint.ts` + `file_meta` | 采样哈希（头尾各 4 MiB）+ 完整 sha256，已有「后台算、202 立即返回、结果写事件流」的现成范式（`file-meta/checksum`） | `checksum` 路由要求先有 `file_meta` 行（`checksum/route.ts:41`），游离文件没有 |

**关键的现成资源**：HF 的 LFS `oid` **就是文件内容的 sha256**（`hf/client.ts:17-21`），且一路透传到了前端
（`core/quant.ts:25` `RepoFile.oid` → `repo-detail-view.tsx:59` `RemoteFile.oid`）。它目前只被下载完成后的
校验用到（`toDownloadFile`，`repo-detail-view.tsx:120`），**匹配层完全没用它**。这是本设计精度提升的地基，
不需要新增任何数据来源。

**完全空白的**：硬链接。全库没有一处 `linkSync`（只有 `docs.test.ts` 用过 `symlinkSync` 造测试用例）。

### 3.2 设计推演补充（已获用户确认）

| # | 决策 | 理由 |
|---|---|---|
| D11 | 占盘按 inode 去重 | `decorateProfileStats`（`repoProfiles.ts:114`）按目录前缀 `sum(size)`，硬链接会让两个档案各报一次完整大小而磁盘只占一份。不去重是误导，等于 bug |
| D12 | 保留现有的进页面自动扫 | 零成本、已在跑；新增的「扫描」按钮是**带自定义目录的深度扫描**，范围更大，两者不冲突 |
| D13 | 服务端重新验证前端传回的源路径 | 扫描结果不入库，确认时源路径由前端带回。服务端必须重扫确认「确实存在、L1 仍匹配、落在允许范围内」，与 README-LLM 批的「前后端各回证一次」同一模式 |
| D14 | 远端无 `oid` 时禁用移动/链接 | 非 LFS 文件没有内容哈希可比对，L2 无从确认。宁可多下一份，不能凭名字和大小挪一个无法证实的文件 |
| D15 | 不做软链接 | 跨文件系统场景已由复制覆盖；且软链接指向 models 外的路径，在 llama.cpp 容器内必然失效（它只挂 models 根） |

### 3.3 命名约定

- 「获取（acquire）」：下载 / 移动 / 链接 / 复制四种手段的统称，新 API 与新模块用它命名
- 「游离（unclaimed）」：`refs === 0` 的文件。**不要**与 `file_meta` 的「孤儿（orphan）」混用——
  后者语义相反，指「元信息行还在、磁盘文件没了」（`fileMeta.ts:101`）
- 「在别处（stray）」：现有词，指本档案远端清单里有、本地在档案目录外已存在的文件。本期语义扩大到
  「包括在别的档案目录内」

## 4. 概念模型与匹配规则

### 4.1 游离的唯一定义

```
游离 = refs === 0（buildRefMap 补集）
  ├ 标签 inRepo   ：是否落在某个 HF 档案目录内（repoDirOf）
  └ 标签 hasMeta  ：是否有 file_meta 行（有则带用户手填的量化标签 / 备注）
```

两个标签只影响展示与可选动作，不影响判定本身。

**硬链接产生的第二个路径同样算游离**，这是正确的——它确实还没被任何配置引用。展示时加「与
`<另一路径>` 共用」标签即可，不做特殊排除。

### 4.2 候选匹配分两级

| 级别 | 判据 | 时机 | 成本 |
|---|---|---|---|
| L1 快筛 | `size` 精确等于远端声明 **且**（`basename` 相同 **或** 本地已缓存的 `full_sha256` 等于远端 `oid`） | 扫描时 | 零 IO（size 来自 `scanTree` 已有的 stat） |
| L2 确认 | 完整 sha256 == 远端 LFS `oid` | 用户点确认后 | 流式读一遍源文件 |

L1 的第二个分支是跨仓库复用的关键：`unsloth` 与 `bartowski` 的同一份 mmproj 文件名往往不同
（`mmproj-F16.gguf` vs `Model.mmproj-f16.gguf`），只按 basename 必然漏掉。有缓存哈希时按内容认，
是这条路径唯一可靠的判据。

远端 `oid` 缺失（非 LFS 文件）时，该行**只能下载**，动作下拉禁用并给出原因（D14）。

### 4.3 动作矩阵

| 已有文件在哪 | 移动 | 硬链接 | 复制 | 默认 | 备注 |
|---|:--:|:--:|:--:|---|---|
| models 内，非档案目录 | ✅ | ✅ | — | 移动 | 同一文件系统，`renameSync` 毫秒级。原位置是游离文件，留一份链接没意义 |
| models 内，另一个档案里 | ❌ | ✅ | — | 硬链接 | 移走会掏空那个档案（`planFileMove` 本就拒绝从档案目录移出，`filesApi.ts:556`） |
| 自定义目录（models 外） | ✅ | ❌ | ✅ | 复制 | 跨挂载点：`rename` 抛 EXDEV、硬链接跨文件系统不成立。此处的「移动」= 复制后删源 |
| 本地没有 | — | — | — | 下载 | — |

### 4.4 分片组语义

远端一个量化组可能是多个分片文件（`model-00001-of-00003.gguf` …）。**动作按组选，判定与执行按文件**：

- L1 匹配对组内每个文件独立进行，因此完全可能出现「3 片里本地已有 2 片」
- 组的默认动作取组内**已有文件**的位置推出（按 §4.3 矩阵）；组内没有对应本地文件的分片，
  该文件走下载
- 一次确认里，同一组的「移动 2 片 + 下载 1 片」属于**同一个 batch**，归档与进度按批次统一收口
- 现状 `mergeRepoRows` 对分片组只记一个 `strayRel`（`repo-files-view.ts:131` 的
  `if (strayRel === null)` 分支），本期改为逐分片记录，否则多分片组只能认出一片

## 5. 数据模型（migration v17）

纯追加，旧代码忽略即可回滚：

```sql
ALTER TABLE download_tasks   ADD COLUMN source_path  TEXT;  -- 本地源，panel 视角绝对路径
ALTER TABLE download_tasks   ADD COLUMN local_action TEXT;  -- move | link | copy
ALTER TABLE download_history ADD COLUMN source_path  TEXT;
ALTER TABLE download_history ADD COLUMN local_action TEXT;
```

- `source` 列增加 `"local"` 取值。该列是裸 `TEXT NOT NULL` 无 CHECK 约束（`migrations.ts:222`），
  加取值零 schema 阻力
- 两列对 `"hf"` / `"url"` 任务恒为 NULL
- `source_path` 统一存 **panel 视角绝对路径**（不是相对路径）——models 外的源必须是绝对路径，
  统一一种形态免去调用方判断
- `download_history` 同步加两列，否则归档后看不出这批是下来的还是挪来的

### 5.1 `file_meta` 的口径扩成 union

现状 `listFileMeta` 只遍历模型配置引用过的路径（`fileMeta.ts:239-254`）。本期改为
「配置引用的路径 ∪ 游离文件」。目的有二：

1. `full_sha256` 有地方缓存，L2 校验算过一次下次免算
2. 交付 C 的「有备注」标签靠它成立

**models 外的文件不登记**：`file_meta.path` 受 `ggufPathSchema` 约束，必须是 models 根内的相对路径。
外部导入是一次性动作，导入完文件就在库内了，不值当为它改 schema。

**影响范围**：`file-meta/checksum` 路由的前置校验（`checksum/route.ts:41` 的
`SELECT 1 FROM file_meta`）随之自然放行游离文件——它们现在有行了。

### 5.2 `fsScanner.ModelFile` 加 `ino`

```ts
export interface ModelFile {
  rel: string;
  size: number;
  mtime: number;
  ino: number;   // 新增：硬链接去重用
}
```

`statSync` 返回值里本来就有 `ino`，取一下是零成本。**影响范围**：`scanTree` 的全部调用方
（`filesApi.ts`、`repoProfiles.ts`、`fileMeta.ts`、`folders.ts`、`repos/[id]/files/route.ts`），
但都是纯追加字段，不改现有行为。`decorateProfileStats` 的 `bytes` 改为按 `ino` 去重后求和（D11）。

## 6. 路径映射与自定义目录

### 6.1 面板自己发现可用路径，不让用户手写映射

`getPathMaps()` 现在只有 models 一组（`pathMaps.ts:11` 的注释已预留扩展位：「后续 panel.yaml
增加 config 等映射组时，只需在数组里补一项」）。本期扩成：

```
models 那组（现有优先级链不动）
  + 自身容器挂载表里发现的其余 bind
```

`selfMounts` 已有的 `inspectMounts(selfContainerId())` 返回 `(source, destination)` 对，
**本身就是 `PathMap` 的形状**。排除面板运行必需的三项——`/app/config`、`/host/proc`、
`/var/run/docker.sock`——其余即为可用的导入源。

三个连带收益：

1. 用户按项目一贯约定填**宿主机路径**（CLAUDE.md 的核心设计要点：所有配置路径以宿主机视角书写），
   换算由 `toPanel` 自动完成
2. 填了个没挂载的路径时能给出准确诊断——「该路径在面板容器内不可见，需在 `docker-compose.yml`
   增加挂载」并列出当前可用的，而不是误导性的「目录不存在」。这个区分很重要：面板是容器，
   compose 只挂了 4 样东西（docker.sock、`./data`、`./models`、`/proc`），用户填
   `/home/xxx/Downloads` 时 `readdirSync` 报 ENOENT，真实原因是没挂载而不是路径不对
3. 顺手补上 `CLAUDE.local.md` 待办 2「路径映射编辑」的一半——面板自己发现，不需要用户手写映射

### 6.2 自定义目录的持久化

存 `settings` 表（key: `scan_extra_dirs`，值为宿主机路径数组的 JSON），复用现成的
`/api/v1/settings/[key]` 路由。填一次下次还在。

## 7. 执行层

### 7.1 队列改造：`manager.ts` 只开两处分支

```
buildRequest        →  source === "local" 时不拼 HTTP 请求
执行器选择           →  source === "local" 时走 runLocalAcquire，不走 startDownload
```

队列编排、失败计数、`MAX_CONSECUTIVE_FAILURES` 停摆保护、批次归档（`archiveIfBatchDone`）
**与源无关，一行不动**。这是把风险控制在可接受范围的关键：`manager.ts` 是 699 行 + 45KB 测试的
下载队列心脏，上一批设计文档自己称它「本设计风险最高的部分」。

### 7.2 `runLocalAcquire` 两阶段

```
阶段 1  校验：流式读源文件算 sha256，与任务的 expected sha256 比对
              进度 = 已读字节 / 总字节
              不符 → 任务 failed，error 明确写「内容不符」，前端据此提示「已改为下载」

阶段 2  执行：move  → renameSync（毫秒）
              link  → linkSync（毫秒）
              copy  → 流式复制到 <target>.part 再 rename（沿用下载器的原子落盘手法）
                      进度 = 已复制 / 总量
              移动（models 外）→ copy 成功后 unlink 源

**本地复制不支持续传**：下载器的续传靠 `.part.meta.json` 里的 url/etag 判定同一来源
（`downloader.ts:248-276`），本地复制没有这两样东西可比对，硬做等于凭路径猜。取消或失败时
直接删掉 `.part`，重来一遍即可——本地盘复制的重来成本远低于网络下载，不值得为它造一套
本地续传的元数据。
```

- 进度节流沿用现有的 `progressIntervalMs`（默认 500ms 写库）
- 取消/暂停：阶段 1 与阶段 2 都在流式循环里检查中断标志，与下载器同款
- `copy` 阶段的 `.part` 中间态复用 `download-part.ts` 的后缀常量，因此
  `repo-files-scan.isPartial` 天然把它滤掉，不会在扫描里被当成「已存在的文件」

### 7.3 跨盘失败的兜底

现有 `moveFiles` 的裸 `renameSync` 若遇 EXDEV 会冒泡成无错误码的 500（`fileMove.ts:84-86`）。
本期在 `runLocalAcquire` 内捕获 EXDEV 并转成明确错误码 `CROSS_DEVICE`，前端提示「源与目标不在同一
文件系统，请改用复制」。**不改 `fileMove.ts` 本身**——那是另一条路径（文件页的手动移动），
本期不扩范围。

## 8. API

| 接口 | 语义 |
|---|---|
| `POST /api/v1/repos/:id/scan` | 深度扫描：models 树 + 自定义目录，与本档案远端清单跑 L1 快筛。返回候选与各行可选动作。**不入库** |
| `POST /api/v1/repos/:id/acquire` | 统一提交入口。body：`{ items: [{ file, action, sourcePath? }] }`。服务端重新验证后分派：`download` → `enqueueDownload`；`move`/`link`/`copy` → 入 local 队列任务。**替换** `POST /repos/:id/download`（只有档案页一个调用方，直接迁移，不留两个入口） |
| `GET /api/v1/files/unclaimed` | 交付 C 的全库游离清单：`refs===0` 的文件 + `inRepo` / `hasMeta` 两个标签 + inode 共用信息 |
| `GET/PUT /api/v1/settings/scan-dirs` | 自定义目录，复用现成 settings 路由 |

### 8.1 服务端重新验证（D13）

`acquire` 对每个 `action !== "download"` 的条目校验三件事，任一不过即 400：

1. `sourcePath` 解析后确实存在且是普通文件
2. L1 仍然匹配（size 等于远端声明；basename 或缓存哈希命中）
3. 路径落在允许范围内：models 根内，或已配置的 `scan_extra_dirs` 之一内（归一化后前缀判定，
   复用 `core/paths.isInside` 的目录边界语义，防 `/models` 与 `/models2` 误匹配）

前端篡改绕不过去。

### 8.2 批次归属

**一次确认产生一个 batch**，其中混合 `download` 与 `local` 两类任务。归档
（`archiveIfBatchDone`）与下载页分组因此不需要任何改动——它本来就是按 `batch_id` 收口的
（`manager.ts` 的 D14 决策）。

## 10. 边界（明确不做）

| 不做 | 原因 |
|---|---|
| 软链接 | 跨文件系统场景已由复制覆盖；软链接指向 models 外的路径在 llama.cpp 容器内必然失效 |
| 任何自动执行 | 一律用户确认后才动文件。与既有「自动寻找不静默改写配置」的风格一致 |
| models 外文件的 sha256 缓存 | 一次性动作，导入完文件就在库内了 |
| URL 直链下载的本地复用 | 没有远端清单可比对 |
| 存量文件的批量归位工具 | 本期是「获取时不重复」，不是「整理已有库」 |
| 改 `fileMove.ts` 的跨盘兜底 | 那是文件页手动移动的路径，与本期无关，不扩范围 |
| 档案的定时刷新 / 新量化推送 | 沿用上一批边界，YAGNI |

## 13. 验收要点

1. 档案里一个量化已在 models 别处 → 扫描后行显示「在别处」且**可勾选**，确认弹层默认「移动」
2. 同一份 mmproj 已在另一个档案目录内 → 行显示「在另一档案」，移动禁用、默认「链接」，
   执行后两个档案都能看到该文件，**磁盘占用只增加 0**
3. 档案列表页两个档案的「占盘」之和不再把共用文件算两次（D11）
4. 故意改坏一个同名同大小的文件 → 确认后校验不通过，该行报「内容不符」并可一键改为下载
5. 远端某文件无 `oid`（非 LFS）→ 动作下拉禁用并给出原因，只能下载
6. 自定义目录填一个没挂载的宿主机路径 → 提示「容器内不可见，需在 compose 增加挂载」并列出可用路径，
   **不是**「目录不存在」
7. 自定义目录填一个已挂载的路径、里面有匹配文件 → 默认「复制」，可改「移动」，
   移动执行后源文件消失
8. 复制 88 GB 文件过程中点取消 → 任务停止，`.part` **被删除**（本地复制不续传，§7.2），目标位置无半成品
9. `/files` 二级栏「未登记」格子计数与实际游离文件数一致；建配置深链可用；归位可用
10. 文件选择弹层里未被引用的文件带「未被使用」徽标
