# 版本漂移与手动关联 · 设计文档

> 2026-09-04 头脑风暴定稿。上游是 `2026-09-03-本地权重迁移-design.md`（下称「迁移设计」），
> 本文修正它的两处语义缺口并补一个用户逃生口。

## 1. 问题

三件事，同一个根因。

**① 档案页对「本地这份文件到底是什么」只有二值判断，而且档案内外用了两套口径。**

| 位置 | 现在的口径 | 后果 |
|---|---|---|
| 档案目录**内**（`local` 路） | 只比 basename，不看 size | 远端换版本后陈旧副本仍显示「已下载」，用户无从知道它过期 |
| 档案目录**外**（`strays` 路） | basename + size 精确相等 | 不中就完全沉默，只剩「下载」按钮 |

真机实例（2026-09-04 实测）：`unsloth/Qwen3.8-27B-GGUF` 档案页对
`Qwen3.8-27B-UD-Q4_K_XL.gguf` 只给「下载」，而 `models/qwen3.8/` 下就躺着一个同名文件。
原因是本地 17,923,394,624 字节、远端声明 17,559,178,144 字节，差 347.3 MiB——unsloth 重传过
这个 UD 量化。面板的拒绝是对的（内容确实不同），但它一个字都没说。

**② 被模型配置引用的候选文件默认动作是「移动」，搬完配置就悬空。**

`actionsFor` 的动作矩阵只看 `inModelsRoot` / `inRepoDir` / `oid` 三维，没有「是否被配置引用」这一维。
一个在 models 根内、不属于任何档案、但被某个模型配置引用的文件，匹配上之后默认 `move`；
而 `localAcquire.ts` 全文不碰 `models` 表——文件搬走，配置还指着旧路径，模型起不来。
对比：档案页原有的「归位」按钮走 `planFileMove`，那条路径**会**事务重写配置引用。
所以这是 acquire 相对既有功能的一处倒退，不是历史包袱。

**③ 用户比面板更懂时没有逃生口。** 用户明知盘上那份是对的（只是旧版本），面板不给任何手动途径。

## 2. 现状盘点（调研结论，2026-09-04 实测）

- **代码里没有任何 git / git-lfs 调用**，下载器是自研 fetch + Range 断点续传。
- `repo_files_cache` 只存 `repo / groups / fetched_at`，不存 revision；但 `groups` 里每个
  `RepoFile` 带 `oid`（HF 的 LFS oid **就是文件内容的 sha256**）。
- `download_tasks` 在真机上是空表——现有模型全是用户用 hf CLI 手动下的，从没经过面板下载器。
  因此 `file_meta.full_sha256` 全为 null（播种源为空），只有 `sample_sha256`。
- **hf CLI 会在同目录留下边车** `.cache/huggingface/download/<basename>.metadata`，三行分别是
  commit hash（40 hex）、**etag（64 hex）**、时间戳。实测验证（`qwen3.8/mmproj-F16.gguf`，927 MB）：

  ```
  边车第二行 cbb841a9ee0636b2ec172f5bb8df2ea8dfeb01e90fe7c6126581d662a0b4e43e
  实算 sha256 cbb841a9ee0636b2ec172f5bb8df2ea8dfeb01e90fe7c6126581d662a0b4e43e
  ```

  即：**手动下载的既有文件也能零成本拿到精确 oid**，不必读满 17 GB 算哈希。
- `fileMove.ts` 的 `planFileMove` 产出 `refUpdates`，全部 rename 成功后在单个
  `db.transaction()` 内批量重写 `gguf_file` / `mmproj_file`。
- `src/components/models/model-file-picker.tsx` + `src/lib/model-file-picker.ts` 已是一个
  按目录分组、不硬过滤、判定已下沉的选择弹层；`PickerItem` 已带 `refs`（引用计数）。
- `collectScanCandidates` 深度扫描时已经遍历整棵 models 树，未匹配上的候选目前被丢弃。

## 3. 决策清单（用户 2026-09-04 拍板）

| # | 决策 | 用户选择 |
|---|---|---|
| D1 | 目的 | 「我要知道手上这份过期了没」——不做多版本共存 |
| D2 | 检测时机 | 进档案页自动跑，**只用零成本信号**；拿不到 oid 就说「无法判定」并给手动校验按钮，绝不偷偷算 17 GB |
| D3 | 过期后的动作 | 标记 +「更新到最新版」，但该文件正被**运行中**的模型占用时禁用并说明原因 |
| D4 | 被配置引用的候选 | 两条都做：动作矩阵补一维（默认降为 `link`）**且**新增显式的「移动并更新配置」 |
| D5 | 手动关联的默认动作 | 默认 `link`，`move` 可选 |
| D6 | 手动关联的候选范围 | models 内**全部未归档文件**，不限名、不限大小 |
| D7 | git 初始化 | 不做（理由见 §10） |

### 3.1 术语更正

迁移设计 §4.1 把**「游离」**定义为 `refs === 0`（没有任何配置引用）。本文要表达的是
`inRepoDir === null`（不属于任何档案目录），且**明确允许有配置引用**。两个定义会打架，
故本文一律使用**「未归档文件」**指代后者，代码与文案同步采用该词；「游离」保持迁移设计的原义不变。

## 4. 三值匹配模型

### 4.0 「配对」与「判定」必须拆成两步

这是本设计最容易做错的地方。现在 `matchLocalCandidate` 把两件事糅在一起：
size 不等就直接 `continue`，于是「配对不上」和「配对上了但版本不同」变成同一件事——
这正是 §1① 那个沉默的来源。拆开：

- **配对**（谁对应谁）：basename 相等，或（远端 oid 可用且）本地 `full_sha256` 与之相等。
  **不再看 size。**
- **判定**（配上的这一对是什么关系）：由下表的三值给出，size 在这一步才参与。

同名候选可能有多个（不同目录下各一份，大小各异）。配对时按
**`same` > `unknown` > `different`** 取最优的那个，同状态取先遇到的。
这条排序保证「真身在别处、另有一个同名但对不上的文件」时不会先到先得（迁移设计 I4 的老问题）。

`different` 只影响**动作可用性**（不给迁移动作，只能下载或走 §7 手动关联），
不影响它是否出现在界面上——出现并说清楚，正是本设计要的。

### 4.1 判据

判据只看手上有什么证据：

| 状态 | 判据 | 成本 |
|---|---|---|
| `same` | 两边 oid 都有且相等 | 零 |
| `different` | 两边 oid 都有且不等，**或** size 不等 | 零（size 不同则内容必然不同） |
| `unknown` | size 相等但至少一边缺 oid | 零 |

判定纯函数下沉 `src/lib/version-drift.ts`，签名形如：

```ts
export type DriftState = "same" | "different" | "unknown";
export function compareToRemote(
  local: { size: number; oid: string | null },
  remote: { size: number; oid?: string },
): DriftState;
```

`oid` 一律要求 64 位小写十六进制（复用 `lib/acquire-match.ts` 已有的 `SHA256_PATTERN`）；
格式不合法视同没有。

### 4.2 本地 oid 的三个来源

按优先级取第一个可用的：

1. **`file_meta.full_sha256`** — 面板下载的文件由 `download_tasks.sha256` 播种，链路现成
2. **hf CLI 边车** — 读 `<dir>/.cache/huggingface/download/<basename>.metadata` 第二行。
   三条防御缺一不可（边车是 `huggingface_hub` 的内部实现细节，随时可能变）：
   - 文件恰好 3 行
   - 第二行匹配 `SHA256_PATTERN`
   - **gguf 的 mtime 不晚于边车的 mtime**——晚了说明文件在下载完成后被改动过，边车记的 oid 已不代表当前内容
3. **手动完整哈希** — 已有的 `POST /api/v1/file-meta/checksum`（202 + 事件流），只在用户点「校验」时触发

三者都拿不到就是 `null`，配合 size 判据仍能给出 `different` 或 `unknown`，绝不阻塞页面。

边车解析下沉 `src/lib/hf-sidecar.ts`（纯函数，输入是文件内容字符串 + 两个 mtime），
读盘那层留在 `src/server/`。

## 5. 三处表现

### 5.1 档案目录内的文件

| 状态 | 行上表现 |
|---|---|
| `same` | 「已下载」（现状不变） |
| `different` | 「已下载 · 有更新」+「更新到最新版」按钮 |
| `unknown` | 「已下载」+ 淡色「未校验」标记，点击触发手动完整哈希 |

注意这是**新增能力**，不是改判：现在档案目录内只按 basename 匹配，一律显示「已下载」。
新口径不会让任何已下载的文件变成「未下载」。

### 5.2 档案目录外的同名文件（迁移候选）

| 状态 | 行上表现 |
|---|---|
| `same` | 正常给出迁移候选（现状） |
| `unknown` | 正常给出迁移候选，标注「未校验，执行时会做完整校验」 |
| `different` | **不再沉默**：说明「本机有同名文件，但与远端当前版本不符（大 347 MiB）」，动作只有下载，另给「手动关联」入口（§7） |

`unknown` 作为候选是安全的：`localAcquire` 执行时本就会算 sha256 与远端 oid 比对，
不符则任务失败并可一键退回下载（迁移设计 §13 第 4 项）。

**无回归**：今天能当候选的（size 精确相等）在新口径下必是 `same` 或 `unknown`，一个不少。

### 5.3 「更新到最新版」

- 复用现有下载队列 `enqueueDownload`，目标路径不变。`partitionExistingTargets` 的判据是
  「已存在**且 size 相符**才跳过」，新版 size 不同故不会被跳过，正常入队重下；
  下载器写 `.part` 后 rename 覆盖，天然满足原子替换。
- **占用中拒绝**：该文件被**当前运行中**的模型配置引用时按钮禁用并说明原因。
  llama.cpp 是 mmap 读的，就地覆盖会让正在跑的推理读到半新半旧的字节。
  运行中模型取自现有的运行时单例（单模型设计），不新增状态。
- 覆盖确认框里列出引用该文件的模型配置名——被引用不阻断，但用户要知道。

## 6. 移动语义修正（D4）

### 6.1 动作矩阵补「被配置引用」一维

`actionsFor` 增加入参 `referenced: boolean`（候选是否被任何模型配置引用，来源是现成的
`buildRefMap`）。`referenced === true` 时从 `actions` 中**移除裸 `move`**、补入
`move-with-refs`，`defaultAction` 降为 `link`：

| 位置 | `referenced === false`（现状） | `referenced === true`（新） |
|---|---|---|
| models 根内、不属于任何档案 | `[download, move, link]`，默认 `move` | `[download, link, move-with-refs]`，默认 `link` |
| 在别的档案目录内 | `[download, link]`，默认 `link` | 同左（档案内的文件本就不给移动） |
| models 根外（自定义目录） | `[download, move, copy]`，默认 `copy` | 同左（见下） |

理由：`link` 之后原路径与档案路径同 inode，配置照旧可用、不额外占盘，是这个场景下的正确默认。

**models 根外的候选 `referenced` 恒为 false**：`buildRefMap` 的键是 models 根相对路径，
根外文件不可能被配置引用（`gguf_file` 受 `ggufPathSchema` 约束必须是根内相对路径）。
实现上不要给根外候选去查引用表，直接置 false 并注释说明。

### 6.2 新增动作 `move-with-refs`

显式的「移动并更新配置」：搬完在同一事务内把引用它的配置改指到新路径。
复用 `fileMove.ts` 的 `planFileMove` / `refUpdates` 机制，不另写一套重写逻辑。

`referenced === false` 的候选不提供这个动作（没有引用可更新，裸 `move` 即可）。

**glob 引用一律拒绝**（实施中补的边界，见 §13.2）：配置字段若是 `main/m1-*.gguf`
这样的分片 glob，把它改写成单个新路径会毁掉组内其余分片的解析。这类情况引导用户
走档案页的「归位」——`planFileMove` 本就是整组语义。

### 6.3 服务端重验相应扩展

`acquireGuard.assertActionAllowed` 复算 `actionsFor` 时同样要传 `referenced`
（服务端自己查 `buildRefMap`，不信前端）。`move-with-refs` 与 `move` 在矩阵里是两个动作，
各自的位置约束一致。

## 7. 手动关联（逃生口）

### 7.1 形态

档案页任一「未下载」或「有更新」的行上给一个次要入口「手动关联本机文件」，
打开泛化后的文件选择弹层，用户选一个文件，然后按 §7.3 的动作执行。

**本质是 move/link + rename**：档案目录里的文件名必须是远端那个名字，否则档案页照样匹配不上。
好消息是这个能力**已经现成**——`target_rel = targetDir + "/" + <远端文件名>`，
而 `sourcePath` 是本地任意路径，`runLocalAcquire` 天然就是「搬到目标路径并采用目标文件名」，
不需要新的重命名逻辑。

顺带的收益：能关联**不同名**的文件（本地叫 `qwen38-27b.gguf` 也能关联到
`Qwen3.8-27B-UD-Q4_K_XL.gguf`）。

### 7.2 候选范围（D6）

models 根内的**全部未归档文件**（`inRepoDir === null`），不限名、不限大小。
弹层把「同名的」「大小接近的」排在前面做引导，但**不阻断**——用户比面板更懂是这个功能的前提。

数据来源是白拿的：`collectScanCandidates` 已经遍历过整棵 models 树，
把未匹配上的未归档候选一并放进 scan 响应即可，不新开 API、不再扫一次盘。

分片组**逐文件关联**，不做整组推断——多分片要选多次，但这是罕见的救济动作，不值当。

### 7.3 动作与配置迁移

默认 `link`（D5），`move` / `move-with-refs` 可选，规则与 §6 完全一致：
被配置引用的文件若选移动，走 `move-with-refs` 把配置一起改指。

### 7.4 事后表现

搬进档案目录后，§4 的三值判定会如实把它标成 `different`（「已下载 · 有更新」）——
它确实不是远端当前版本。同时在 `file_meta.mark` 写一条「手动关联，非远端当前版本」的备注
（字段现成，不需要迁移），用户日后仍看得见来龙去脉。

## 8. 安全边界

手动关联放宽的**只有**「内容与远端声明相符」这一条。其余每一条都保留，
而且保留的每一条服务端都能自己算，不依赖前端传什么：

| 校验 | 常规 acquire | 手动关联 |
|---|---|---|
| 路径落在 models 根内（字符串级 + realpath 级两道） | 保留 | **保留** |
| 不属于任何档案目录（服务端 `repoDirOf` 重算） | —— | **保留** |
| 存在且是普通文件 | 保留 | **保留** |
| 动作矩阵（§4.3 + §6） | 保留 | **保留** |
| L1：size / oid 与远端相符 | 保留 | **放宽** |
| L2：执行时 sha256 与远端 oid 比对 | 保留 | **放宽** |

协议上用一个显式字段承载，而不是靠「缺字段就放宽」：`AcquireSubmitItem` 增加
`manual?: true`。服务端见到 `manual === true` 时跳过 L1 的 `MISMATCH` 判定，
并在入队时把 `sha256` 置空（`localAcquire` 见 `sha256 === null` 即只算不比，
把算出的值写回 `file_meta.full_sha256`——这一趟哈希是执行期本就要做的，不额外加成本）。

越权路径、别的档案里的文件、非法动作，一条都过不去。

## 9. 数据模型与 API

**无需 migration。** 本设计不新增列：

- 本地 oid 复用 `file_meta.full_sha256`
- 手动关联的备注复用 `file_meta.mark`
- 远端 oid 已在 `repo_files_cache.groups` 的 JSON 里

**API 改动：**

| 端点 | 改动 |
|---|---|
| `GET /api/v1/repos/:id/files` | `local[]` 与 `strays[]` 各增 `drift: DriftState` 与 `localOid: string \| null` |
| `POST /api/v1/repos/:id/scan` | 组内 `files[]` 增 `drift`；响应增 `unarchived[]`（手动关联弹层的候选池） |
| `POST /api/v1/repos/:id/acquire` | `items[]` 增 `manual?: true`；`action` 枚举增 `move-with-refs` |
| `POST /api/v1/file-meta/checksum` | 不变（手动校验按钮复用） |

## 10. 边界（明确不做）

| 不做 | 理由 |
|---|---|
| **git / git-lfs 初始化 hf 档案目录** | 单个 GGUF 17–24 GB，object store + 工作区直接翻倍，与本地权重迁移里程碑刚立的「同一份权重只占一份盘」正面冲突；而我们需要的信息 HF 已经用 LFS oid 给了，绕 git 一圈零收益 |
| **多版本共存与切换** | D1 明确排除；与「只占一份盘」矛盾 |
| **commit 级溯源** | 边车第一行的 commit hash 拿得到，但「你这份是某次提交的」对决策没有增量价值 |
| **对与任何仓库无关的文件判过期** | `models/qwen3.6/` 那类文件没有远端基准，判不了，也不该假装能判 |
| **自动后台补算完整哈希** | D2 明确排除，理由见迁移设计最终审查的 I7（首屏同步采样读把 `/files` 拖垮） |
| **整组手动关联** | §7.2，YAGNI |

## 11. 测试要点

判定一律下沉 `src/lib/`（vitest 是 node 环境无 jsdom，组件测不了）：

- `lib/version-drift.ts`：三值判定的证据组合矩阵（两边有 oid × 相等/不等、size 不等、
  单边缺 oid、oid 格式非法）
- `lib/hf-sidecar.ts`：三条防御各一条用例（行数不对、第二行非 64 hex、gguf mtime 晚于边车）
- `lib/acquire-match.ts`：`referenced === true` 时 `move` 不在 `actions` 里、`defaultAction` 为 `link`；
  `move-with-refs` 的位置约束与 `move` 一致
- `lib/acquire-plan.ts`：`manual` 提交项不带 sha256、动作降级规则不误伤 manual 行
- `server/acquireGuard`：手动关联仍拒绝档案目录内的源、仍拒绝越界路径、仍拒绝非法动作
- `server/download/localAcquire`：`sha256 === null` 时只算不比并回写 `file_meta`
- 「更新到最新版」：目标已存在但 size 不同 → 不被 `partitionExistingTargets` 跳过

## 12. 验收要点

1. 档案页对 `Qwen3.8-27B-UD-Q4_K_XL.gguf` 不再只给「下载」，而是说明本机有同名文件、
   与远端当前版本不符、大 347 MiB
2. 档案目录内放一个陈旧副本 → 行显示「已下载 · 有更新」，点「更新到最新版」能重下覆盖
3. 该文件正被运行中的模型使用时，「更新到最新版」禁用并说明原因
4. 一个被模型配置引用的未归档文件匹配上某档案 → 默认动作是「链接」而非「移动」，
   选「移动并更新配置」后配置的 `gguf_file` 确实改指到新路径，模型仍能启动
5. 手动关联弹层能列出 models 内全部未归档文件（含改过名的），不含任何档案目录内的文件
6. 手动关联一个大小不符的文件 → 执行成功，档案页随后显示「已下载 · 有更新」，

### 13.2 规格补充（实施中发现、设计原文未写的边界）

1. **`move-with-refs` 不支持 glob 引用**（已补进 §6.2）。
2. **手动关联项的 `size` 必须用实测值**。§8 只说放宽内容校验，但执行器的大小校验用的是
   入队时声明的 `expectedSize`；若沿用远端声明的 `rf.size`，手动关联必然因大小不符而失败
   ——放宽内容校验的同时必须把 size 一起换成实测值（`acquire/route.ts` 的
   `size: manual ? st.size : rf.size`）。
3. **「local 任务且入队时 `sha256` 为 NULL 即手动关联」这条不变量有四个消费方**：
   acquire 路由的构造点、`localAcquire.ts`（决定要不要比对哈希）、`manager.ts` 的完成回调
   （写「手动关联，非远端当前版本」备注）、`manager.ts` 的 `enqueueLocal`（绕过存在性跳过判据）。
   它由 `assertRemoteMatch` 唯一的 `return null` 分支（`opts.manual`）加单测加全库唯一调用点
   共同维持，是**运行时约定不是类型保证**——调用点实参 `{ manual: boolean }` 的静态类型
   区分不出两种情形。改动那个分支会同时影响四处。

### 13.3 已知遗留（明确划出去，不是遗漏）

1. **下载队列没有强制覆盖开关**。`compareToRemote` 判 `different` 有两条成因：size 不等，
   或 size 相等而 oid 不等（远端同尺寸重传，如换 imatrix 校准）。而
   `partitionExistingTargets` 的判据是「已存在且 size 相符则跳过」，看不见 oid。于是
   「更新到最新版」对第二条成因 **100% 无效**。本批只把表现改成**如实报告**
   （`updateAllSkipped`：说明这些文件因大小一致被队列跳过、需先删本机副本），
   不再谎报「已加入下载队列（0 个文件）」这条 success。
   手动关联那一半**已修**——`enqueueLocal` 对 manual 项（`sha256 === null`）绕过该判据，
   否则它会被静默丢弃而前端还报「完成」（skipped 计入进度分子）。
   真正的收口要给队列加强制覆盖开关，牵涉 acquire 路由 schema、manager、guard 三处及各自
   测试，明确排除在本里程碑外。
2. **手动关联对 mmproj 行的引导排序偏弱**：弹层按行的 `kind` 传 `field`，但候选池里
   mmproj 的识别靠文件名前缀（社区约定非规范），改过名的投影文件会落在分隔线以下。
   不阻断，仍可选。
3. **`manager.test.ts:1607`「暂停中的 local 任务」用真实 `setTimeout(5ms)` 卡竞态窗口**后断言
   `downloaded_bytes ∈ (0, size*2)`，机器繁忙时会偶发红。属存量测试，非本批引入。
4. **`file_meta` 的 size/mtime 在三处只改 path 的路径上不维护**（`fileMeta.ts` 的 relink、
   `fileMove.ts`、`refRewrite.ts`）：这些路径改了 `file_meta.path` 却不更新 size/mtime，
   于是 `resolveLocalOid` 的新鲜度校验会拒掉那条缓存。后果是**静默降级为「未校验」**，
   不成环（「点击后台补算」现在会连同 size/mtime 一起写回，点一次即可恢复），故不修。
5. **acquire 路由没有服务端的「运行中占用」检查**：D3 定的是前端拦（`lockedRels` 禁用按钮），
   与 `filesApi` 的 move/delete 有服务端 `LOCKED` 守卫形成口径差。危害有限——落盘是
   `.part` + rename 的原子替换，运行中进程握着旧 inode 直到重启。加服务端守卫是新增能力，
   不在本里程碑。
6. **`remoteFileByName` 只留每个 basename 的第一条**：承袭既有的 basename 契约。
   按量化建子目录、每个子目录一份同名 `mmproj-F16.gguf` 的仓库里，两份本地文件的 drift
   会对着同一个远端条目算。同一形状也让 `matchedRemoteGroup` 的 basename 断言失效
   （两个组的 basename 列表完全相同时它抓不到错位）——这两条同源，要改得一起改。
7. **§12 的八条验收要点尚未执行**，分级见 §13.4。
