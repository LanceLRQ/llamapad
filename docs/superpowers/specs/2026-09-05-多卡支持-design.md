# 多卡支持（llama.cpp 多 GPU 调度与配置）· 设计文档

> 日期：2026-09-05 ｜ 状态：设计定稿，未施工
> 前置调研：`docs/_internal/research/05-llamacpp多卡支持与适配调研.md`
> 机器能力划分：`docs/_internal/milestones/23-多卡支持.md`
> 本期只做**单卡机上能完整验收**的部分：后端能力 + 表单校验。监控 UI 与挑卡路径切换挪到多卡机。

## 1. 问题

上游 llama.cpp 的多卡能力齐备且已进化到第二代（`-sm` 四档，官方明确 `row` 已被 `tensor` 取代），
面板一个都没接：全库搜 `split_mode` / `tensor_split` / `main_gpu` 零命中，`buildArgs` 里 GPU 相关
只有 `--gpu-layers` 一条。多卡用户只能手写进 `docker.extra_args`，无校验、无提示、无 UI。

同时存在一个确认的逻辑缺陷：显存 preflight 把所有卡当一个池子求和，不看该模型的 `docker.gpu`。
两张 24G 卡的机器上，模型配了 `device=0`，preflight 报的空闲仍是两卡之和约 48G，判定失真。

| 卸载层数 | `server.gpu_layers` → `--gpu-layers` | `core/args.ts:105-106` |
| **切分策略** | **无** | 全库零命中 |

### 2.1 单卡实测（server-cuda build 10450，Qwen3-1.7B-Q8_0，`--gpus all`）

| 实测项 | 命令片段 | 结果 |
| --- | --- | --- |
| A | `-sm tensor` | 正常 listening |
| B | `-sm tensor --cache-type-k q8_0 --cache-type-v q8_0` | **照常 listening** |
| C | `-dev CUDA0` | 正常 |
| D | `-sm row` | 失败：`device CUDA0 does not support split buffers` |
| E | `-ts 1` | 正常 |
| F | `-sm none -mg 0` | 正常 |
| G | `-sm none -mg 1` | 失败：`invalid value for main_gpu: 1 (available devices: 1)` |

**B 项推翻了原先的乐观假设**：官方文档所述「tensor 模式必须 flash-attn on、KV 不能量化」这组约束，
在单卡下**根本不触发**——tensor 并行退化成单设备，不走多卡 KV 路径。这条直接决定了 §5 的校验口径
必须是警告而非硬拦：硬拦会误伤单卡用户本来能跑的配置。

### 2.2 容器内索引重映射（本设计要解决的核心陷阱）

NVIDIA Container Toolkit 在部分暴露时会把容器内的卡**重新从 0 编号**。`docker.gpu = "device=1,2"`
时，宿主机 GPU1 在容器内是 `CUDA0`。用户写 `main_gpu=1` 以为指向宿主机 GPU1，实际打到宿主机 GPU2。

**两个数字的坐标系不同**：`docker.gpu` 里的编号是宿主机视角，`main_gpu` / `tensor_split` 的顺序是
容器内视角。面板必须替用户翻译，或至少明确告知。本期取「明确告知」（见 §5.2）。

`--list-devices` 无法用于对号入座：打印代码（`common/arg.cpp:2250`）只输出名字与显存，不输出 UUID 或
PCI bus id，两张同型号卡在那份输出里完全无法区分。所以对齐只能靠顺序约定，不能靠标识符匹配。

## 4. 后端能力

### 4.1 设备序注入（A1）

`server/runtime.ts:132-133` 现为：

```ts
const userEnv = merged.docker.env ?? [];
const env = userEnv.length > 0 ? [...userEnv] : undefined;
```

改为调用新纯函数 `buildContainerEnv(userEnv, gpu)`，与 §4.2 的 `visibleDevices` 同落
`src/lib/gpu-visibility.ts`——两者都是「由 `docker.gpu` 推出的容器 GPU 形态」，同源同测同改：

- `gpu === "none"` → 原样返回（空数组时仍返回 `undefined`，保持现状）
- 用户 env 中已存在 `CUDA_DEVICE_ORDER=` 开头的条目 → 原样返回，**用户显式优先**
- 其余情况 → 在数组头部插入 `CUDA_DEVICE_ORDER=PCI_BUS_ID`

作用：`nvidia-smi` 默认按 PCI bus 排序，CUDA runtime 默认 `FASTEST_FIRST`（按算力排），ggml 用
`cudaGetDeviceCount` 直接枚举且不设置该变量。同构多卡两种排序一致；**异构多卡（如 4090 + 3090）会错位**，
面板显示的「GPU 0」与 llama.cpp 的「CUDA0」不是同一张卡。注入后与 nvidia-smi 对齐。

单卡机只能验证「注入后模型照常启动、不回归」。是否真的修正了异构错位，挪机后由 M1 验证。

### 4.2 preflight 按卡过滤（A2）

新建 `src/lib/gpu-visibility.ts`，导出：

```ts
export function visibleDevices<T extends { index: number }>(
  devices: readonly T[],
  gpu: string,
): T[];
```

| `gpu` 取值 | 返回 |
| --- | --- |
| `"none"` | `[]` |
| `"all"` | 全部 |
| `"device=1,2"` | 按 `index` 过滤命中的卡 |
| 未知形态 | `[]` |

未知形态返回空数组，与 `docker-options.ts:38` 把未知形态当 CPU 处理（不设 `DeviceRequests`）的既有
取舍保持一致——宁可降级也不臆测。

放 `src/lib/` 而非挨着 `sumGpuTotals`（`server/metrics/latest.ts`），因为它是**配置语义**不是指标语义，
且表单也要用它算该模型可见卡数（§5.3）。

路由改造（`api/v1/models/[name]/preflight/route.ts`）：现在拿到 model 后直接丢弃，改为保留并合并配置：

```ts
const modelRepo = createModelRepo(getDb());
const model = modelRepo.getModel(name);
if (!model) return 404;
const gpu = mergeConfig(modelRepo.getDefaultConfig(), model.overrides ?? {}).docker.gpu;
const totals = sumGpuTotals(visibleDevices(getMetricsCollector().nvidiaDevices(), gpu));
```

**已知副作用（接受）**：用户写了 `device=5` 但机器只有两张卡时，可见集为空，`sumGpuTotals` 返回 null，
判定退化为 `"unknown"`。这比谎报一个数字好。本期不为此加越界拦截——preflight 只预警不拦截是 U17 的既有定案（见 `milestones/11` §2.5，与本文 D2 无关），
真正的越界提示由 §5.1 的表单校验承担。

**明确不动**运行历史的 `baseline_gpu_mem_mib` / `peak_gpu_mem_mib`（`server/locators.ts:71-72` 同为全池求和）：
peak 来自 `gpu.mem_used_mib` 聚合时序，存储层没有卡维度，只把 baseline 改成按卡会让 `peak - baseline`
两头坐标系不一致。单模型约束下「全池差值 = 该模型占用」仍然成立，净增量口径不失真，留到 §14 一起改。

### 4.3 doctor 报卡数（A3）

`server/doctor.ts` 的 `DoctorDeps` 增加 `gpuDeviceCount: () => number`，`api/v1/doctor/route.ts` 接
`() => getMetricsCollector().nvidiaDevices().length`。

`checkGpu`（`doctor.ts:123-131`）在 `status === "available"` 分支补 detail「检测到 N 张 GPU」，
**且仅在 N 大于零时补**——probe 刚过、tick 尚未跑完时卡数为零，此时说「检测到 0 张」是错的，
保持现状不带 detail。

### 4.4 切分参数一等公民（B1）

`core/schemas.ts` 的 `serverConfigSchema` 扩三字段：

| 字段 | zod 类型 | CLI 参数 |
| --- | --- | --- |
| `split_mode` | `z.enum(["none","layer","row","tensor"]).optional()` | `--split-mode <v>` |
| `tensor_split` | 逗号分隔数值串（如 `3,1`、`0.7,0.3`），`.optional()` | `--tensor-split <v>` |
| `main_gpu` | `z.number().int().min(0).optional()` | `--main-gpu <n>` |

`core/args.ts` 的 `buildArgs` 在 `--gpu-layers` 之后按有无追加，三者均**不配就不下发**。

四条连锁效应，逐条已核实：

1. **`partialServerConfigSchema` 自动跟随**：它是 `z.strictObject(serverConfigSchema.shape).partial()`，
   加字段即自动放行模型级 overrides、参数预设、YAML 导出三处。
2. **bash 导入不用改**：`core/yamlIo.ts:158-159` 的 `SERVER_KNOWN` 直接取 schema shape。
3. **键数断言不用改数字**：`mergeConfig` 是 `{...defaults, ...overrides}` 展开，可选字段不在
   `BUILTIN_DEFAULT_CONFIG` 里，默认场景仍是 server 17 键、扁平 23 键
   （`core/config.test.ts:57-58,112-120,137`）。**新增**一条「覆盖了 `split_mode` 后键数加一」的用例。
4. **`.optional()` 而非 `.default()` 是硬要求**，理由见 D6。

## 5. 校验、坐标系与表单

### 5.1 校验判定（B2）

新建 `src/lib/split-hints.ts`，沿用 `core/gguf-hints.ts` 已有的 `{ field, level, code, values }` 形态，
i18n 按 `code` 渲染。**全部 `level: "warn"`，一条都不硬拦**（D3）。

```ts
export function splitHints(input: {
  splitMode?: string;
  tensorSplit?: string;
  mainGpu?: number;
  cacheK: string;
  cacheV: string;
  flashAttention: string;
  /** 该模型可见卡数；探测不可用时为 null，此时跳过所有与卡数有关的判定 */
  visibleCount: number | null;
}): SplitHint[];
```

| code | 触发条件 | 文案要点 |
| --- | --- | --- |
| `tensorKvQuant` | `split_mode === "tensor"` 且 `cache_type_k` 或 `cache_type_v` 不在 f16/f32/bf16 内 | 点明单卡不触发、多卡下 llama.cpp 可能拒绝。内置「均衡」预设正是 q8_0，是最常见的撞法 |
| `tensorFlashAttnOff` | `split_mode === "tensor"` 且 `flash_attention === "off"` | 官方文档要求 tensor 模式开 flash-attn |
| `rowDeprecated` | `split_mode === "row"` | 官方已用 tensor 取代；附实测证据：本机 3090 上直接 `does not support split buffers` 失败 |
| `mainGpuOutOfRange` | `main_gpu >= visibleCount` | 对齐 llama.cpp 自身报错口径（§2.1 G 项拿到原文） |
| `tensorSplitCountMismatch` | `tensor_split` 项数不等于 `visibleCount` | 项数应与可见卡数一致 |

`visibleCount` 为 null（GPU 探测不可用、纯 CPU 部署）时，后两条与卡数有关的判定整体跳过——
没有卡数就没有越界这个概念，凭空报警是噪音。

**规则可以在单卡机上完整定稿并单测，但「这条校验是不是拦对了」只能到多卡机上证实**（挪机 M2）。
本期不声称已验证拦截效果。

### 5.2 坐标系提示（本设计的重点）

纯函数 `deviceIndexMap` 落 `src/lib/gpu-visibility.ts`（与 `visibleDevices` 同源——两者都在解析
`docker.gpu` 的 `device=` 形态，`visibleDevices` 内部就复用它，避免两份解析各自漂移）：

```ts
/** docker.gpu → 容器内编号对应的宿主机索引；"all" / "none" / 未知形态返回 null */
export function deviceIndexMap(gpu: string): number[] | null;
```

- `"all"` → `null`
- `"device=1,2"` → `[1, 2]`，即容器内编号 0 对应宿主机 GPU1、编号 1 对应宿主机 GPU2
- `"none"` / 未知形态 → `null`

表单在返回非 null 时渲染一行说明：「编号 0 对应宿主机 GPU 1，编号 1 对应宿主机 GPU 2」。

**这条不做，多卡用户会配错卡且毫无察觉**——`main_gpu` 与 `tensor_split` 的顺序都吃这个映射。
它也是本期不切换到 `-dev` 的代价：`--gpus all` + `-dev CUDA0,CUDA1` 能让两个坐标系统一，但那要改
`docker.gpu` 的语义、涉及迁移与文档，且必须先在多卡机确认重映射行为（挪机 M1），本期只做告知。

### 5.3 表单可见性与落点

**可见性（D4 / D9）**：表单复用 `/api/v1/gpu/stats` 取 `devices.length` 作为**整机卡数**，大于一时
展示切分参数区；**已存在覆盖值时无条件展示**，否则从别处导入的配置会看不见也改不掉。越界判定
（§5.1 后两条）用的是 `visibleDevices(devices, gpu).length`，即该模型可见卡数，与可见性用的数不同。

判定下沉为纯函数，与 `splitHints` 同文件：

```ts
export function shouldShowSplitFields(input: {
  deviceCount: number;
  hasOverride: boolean;
}): boolean;
```

**落点清单**（九处，2026-09-05 对照代码核出）：

| 落点 | 位置 | 要做什么 |
| --- | --- | --- |
| schema | `core/schemas.ts` `serverConfigSchema` | 三字段 `.optional()` |
| 键数断言 | `core/config.test.ts` | 数字不改，新增「覆盖后加一」用例 |
| 参数拼装 | `core/args.ts` `--gpu-layers` 之后 | 三个条件下发 |
| 表单草稿 | `lib/model-form.ts` `EDITABLE_KEYS` / `PATH_TO_FIELD` / `DraftState` / `initDrafts` / `deriveOverrides` | 五处同步，草稿键 `splitMode` / `tensorSplit` / `mainGpu`。`initDuplicateDrafts` 委托 `initDrafts`，无需单独改 |

## 7. 边界（明确不做）

| 项 | 为什么不做 |
| --- | --- |
| 分卡监控 UI + dev-only 假多卡数据源 | D2：等多卡机验完带真实需求再做 |
| 挑卡主路径改 `-dev` | 依赖多卡机 M1 的重映射实测结论，现在拍等于猜 |
| 运行历史 baseline / peak 按卡 | §4.2 末段：改一半会让净增量两头坐标系打架 |
| 分卡历史曲线 | 存储层 `metrics_bucket` 无卡维度，改动代价大 |
| 多模型分卡并行 | 被 `server/runtime.ts:19` 的单模型不变量堵死，属 §14 |
| 跨机分布式推理 | `server-cuda` 镜像无 RPC 后端（已核实：无 `rpc-server`，只有 base/cpu/cuda 三个 .so） |

**README 与 AI 推荐参数抽取维持现状**：切分参数**刻意不进**白名单（`lib/readme-params.ts` 的
`ExtractableField` / `SYNONYMS` / `PERF_FIELDS`）。理由是 `-ts 3,1` / `-mg` / `-sm` 是作者机器的拓扑，
不是模型属性，套到用户机上只会错。现状下它们落 `extras` 原样展示（fixture
`lib/__fixtures__/readme/hauhaucs.md:18` 就有 `--split-mode none`），这已是想要的行为。

但要**补一条单测钉住**：schema 加了三字段后，`--split-mode` 仍留在 `extras`、不进 `server`。
`lib/llm-profiles.ts:68` 走 `serverConfigSchema.shape[field]` 只对白名单命中的字段生效，schema 加字段
不会让 AI 抽取自动放行——这条是推理，必须有测试兜底。
