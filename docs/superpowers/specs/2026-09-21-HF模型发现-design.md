# HF 模型发现：模型首页的热门榜与搜索

> 2026-09-21 · 状态：设计定稿，待实现

## 1. 背景与目标

`2026-09-21-模型首页与配置路由迁移-design.md` §7 把「HF 最新排行榜拉取」与「模型搜索」
明确列为延后项，并写下「首页会为它们继续长」。本期就是把那条捡回来。

目标：用户打开 `/models` 就能看见 HuggingFace 上当下最热的 GGUF 仓库，能就地搜索，
看中了两件事一步到位——**把 repo 送进下载弹层**，或**去原站看详情**。

本期**不做**站内的二次浏览（翻页、分面筛选）：结果满一屏就给一条通栏按钮把人送去
HF 站内，那边的筛选器比面板能做的完整得多。

## 2. 已拍板的决策

| 决策点 | 定案 | 理由 |
|---|---|---|
| 落点 | `/models` 首页第三区，不新增路由、不动二级栏 | 上期设计已为它留位；搜索态与热门态共用同一块区域 |
| 榜单口径 | `sort=trendingScore`（HF 站内 Trending 同款） | 下载量榜常年不变，看一次就没有再看的必要；最新发布噪音大 |
| 筛选 | 固定 `filter=gguf`，不给开关 | 面板只跑 llama.cpp，列出非 GGUF 仓库是给用户挖坑 |
| 外链目标 | 跟随设置页 `hf_mirror` 生效端点 | 国内直连 hf-mirror 可用，固定官方站点开是空白页 |
| 满屏出口 | 返回条数 >= 12 时给一条通栏长按钮跳 HF 站内列表页 | 本地不做翻页，复杂度外包给原站 |

## 3. 实测事实（本设计的依据，非推测）

2026-09-21 在 GPU 服务器上实测：

| 请求 | 结果 |
|---|---|
| `huggingface.co/api/models?sort=trendingScore&filter=gguf`（经 `10.22.33.1:20172`） | 200 |
| `hf-mirror.com/api/models?sort=trendingScore&filter=gguf`（**直连，无需代理**） | 200 |
| `hf-mirror.com/api/models?search=qwen3&filter=gguf` | 200 |
| `hf-mirror.com/models?other=gguf&sort=trending` | 200，渲染出与 API 同一批仓库 |
| `hf-mirror.com/models?search=qwen3&other=gguf` | 200 |

两条容易踩的坑，都已验过：

1. **`sort=trendingScore` 不带 `direction` 默认就是降序**（实测 1480 → 478 → 324），
   而 `@huggingface/hub` 的 `listModels` **不支持 `direction` 参数**——正好不需要。
2. `listModels` 默认返回体**不含** `trendingScore`，要靠 `additionalFields: ["trendingScore"]`
   补。但 **`pipeline_tag` 不能放进 `additionalFields`**：它已在库内置的 `MODEL_EXPAND_KEYS`
   里，重复传会让 HF 报 `Array elements must be unique` 直接 400（该字段在返回体里叫 `task`，
   本来就有）。`lastModified` 同样已内置，以 `updatedAt` 的名字直接可用，不必额外要。

3. `ModelEntry` 的精确类型（`node_modules/@huggingface/hub/src/lib/list-models.ts:57`）：
   `updatedAt` 是**真正的 `Date` 对象**（库内 `new Date(item.lastModified)`），
   `gated` 是 **`false | "auto" | "manual"` 三值而非布尔**，`task` 是可选的 `PipelineType`。
   `additionalFields` 的值则是**原样透传**、不做任何转换。三条都直接决定 `toModelSummary`
   怎么写。

## 4. 架构与数据流

```
/models (RSC，已有，force-dynamic)
  └─ <HomeDiscover ownedRepos={…} folders={…} />        ← 新增 client 组件
        │ 挂载后 fetch，不参与 RSC 首屏
        ▼
  GET /api/v1/hf/models?q=&limit=12                      ← 新增 route handler
        │ resolveHfOptions() → { endpoint, token, proxy }（现成，不改）
        ▼
  server/hf/models.ts                                    ← 新增
        │ listModels({ hubUrl, accessToken, fetch: makeProxyFetch, ... })
        ▼
  hf-mirror.com 或 huggingface.co  /api/models
```

**热门榜走客户端取，不进 RSC。** `/models` 是 `force-dynamic` 服务端页，若在服务端取
HF，网络不通时整页会卡在超时上，把「正在运行」「最近更新的仓库」两区一起拖垮。客户端
取则那两区照常秒出，第三区自己转圈/报错，互不牵连。

**复用 `@huggingface/hub` 的 `listModels`，不手写 fetch。** 收益是三件现成的事：镜像端点
（`hubUrl`）、Token 注入（`accessToken`）、代理注入（`fetch: makeProxyFetch`），以及抛出的
`HubApiError` 能直接喂给 `hf/client.ts` 里现成的 `mapHfError()`，翻成 401/403/429 与网络错误
四档中文文案。

为此改造 `mapHfError` 并导出（当前是模块私有函数）。**不能原样复用**：它现在的签名是
`mapHfError(e, repo)`，404 分支写死 `` `仓库不存在: ${repo}` ``，而列表请求根本没有 repo 可传，
硬凑会产出「仓库不存在: 热门榜」这种病句。改成第二参收一句现成的 404 文案：

```ts
export function mapHfError(e: unknown, opts: { notFound: string }): Error;
```

- `listRepoFiles` 传 `` { notFound: `仓库不存在: ${repo}` } ``——行为逐字不变
- `server/hf/models.ts` 传 `{ notFound: "HF 接口不存在，请检查设置页的镜像端点" }`——列表
  端点返回 404 的真实含义就是端点配错了，不是「某个仓库没有」

401/403/429 与网络错误四档措辞由两个调用方共享，不复制一份。

## 5. 接口契约

### `GET /api/v1/hf/models`

| 查询参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `q` | string | `""` | 去首尾空白后为空 → 返回热门榜；非空 → 搜索 |
| `limit` | number | `12` | 非整数 / <1 一律静默回落 12，>50 夹到 50；**不返回 400** |
| `refresh` | `"1"` | 无 | 传 `1` 则绕过缓存强制重取（区块的 `[↻]` 按钮）；仅对热门榜有意义，搜索本就不缓存 |

成功响应（200）。**实现落点**：这个契约已作为 `HfModelsResponse` 落进
`src/lib/hf-models.ts`（route 的返回体用 `satisfies HfModelsResponse` 钉住，客户端组件
import 同一份声明），不再由 route 与客户端各写一份同名不同源的类型：

```ts
interface HfModelsResponse {
  items: HfModelSummary[];
  /** 生效站点根，如 "https://hf-mirror.com"；外链与「更多」按钮都用它组装 */
  endpoint: string;
  /** 缓存写入时刻（epoch ms）；0 = 本次实时取得（搜索恒为 0） */
  fetchedAt: number;
  /** true = 这批是取远端失败后回落的旧数据 */
  stale: boolean;
  /** 回落时带上失败原因；成功为 null */
  error: string | null;
}

interface HfModelSummary {
  repo: string;        // "unsloth/Qwen3.8-27B-GGUF"
  owner: string;       // "unsloth"
  name: string;        // "Qwen3.8-27B-GGUF"
  likes: number;
  downloads: number;
  trending: number | null;   // 搜索结果里 HF 不一定给，缺省为 null
  task: string | null;       // pipeline_tag，如 "text-generation"
  updatedAt: number;         // epoch ms
  gated: boolean;            // 受限仓库，卡片上标锁
}
```

失败响应（502）：`{ "error": "<中文原因>" }`。沿用 `hf/repos/[id]/files/route.ts` 立下的
约定——上游取数失败一律 502 而不透传 HF 的状态码，面板 API 的 404 保留给「面板资源不存在」。
**仅当无旧缓存可回落时才走这条**；有旧缓存则返回 200 + `stale: true` + `error`。

`limit` 同时被 route 与客户端使用，提成 `src/lib/hf-models.ts` 的
`export const HF_DISCOVER_LIMIT = 12`，两处 import 同一个常量，避免「客户端按 12 判满屏、
服务端按 20 返回」这类错位。

**查询参数不用 zod 解析**：全库 `src/app/api/v1` 下没有任何一个 route 用 zod 解析查询串
（zod 只用在请求体上）。既有约定是两种——`events/route.ts` 手工解析后静默回落默认值，
`metrics/window/route.ts` 把判定收敛进纯函数 `parseRangeKey` 再由 route 决定状态码。
本接口取两者的合流：解析逻辑下沉成 `lib/hf-models.ts` 的纯函数 `parseLimit`（可单测），
非法值静默回落而不是 400——`limit` 只是一个展示条数，一个写错的查询串不该让整块区域报错。

## 6. 服务端模块 `src/server/hf/models.ts`

```ts
export interface ListModelsResult {
  items: HfModelSummary[];
  fetchedAt: number;
  stale: boolean;
  error: string | null;
}

/** 本文件自己声明的调用参数，不 import 库的类型；字段即本模块真正会传的那几项 */
export interface ListModelsParams {
  hubUrl?: string;
  accessToken?: string;
  fetch?: typeof fetch;
  sort: "trendingScore";
  limit: number;
  search: { tags: string[]; query?: string };
  additionalFields: string[];
}

export type ListModelsFn = (params: ListModelsParams) => AsyncIterable<ModelEntryWithExtras>;

export interface ListModelsDeps {
  hf: HfOptions;
  limit: number;
  refresh?: boolean;           // true = 绕过缓存强制重取（route 的 ?refresh=1）
  now?: number;                // 测试注入；生产不传，取 Date.now()
  listModels?: ListModelsFn;   // 测试注入；生产不传
}

export async function getTrendingModels(deps: ListModelsDeps): Promise<ListModelsResult>;
export async function searchModels(query: string, deps: ListModelsDeps): Promise<ListModelsResult>;
```

**注入点为什么不是 `typeof hubListModels`**（本节初稿这么写，实现改了，不是擅自改签名）：
库的 `additionalFields` 形参类型 `ModelAdditionalField` 派生自 `MODEL_EXPANDABLE_KEYS`，
而那个数组的 21 个键里**没有** `trendingScore`（2026-09-21 打印实测），`ModelDerivedFields`
也只有 `filePaths`——所以 `additionalFields: ["trendingScore"]` 根本不是库签名的合法实参，
标成 `typeof hubListModels` 在 tsc 下过不去。运行时没问题：库把未知字段原样拼进 `expand=`
再原样回填。于是注入点用本文件自声明的 `ListModelsFn`，生产实现处做一次 `as unknown as`
显式桥接并把上述理由写在注释里。`ListModelsParams` 也刻意不写成 `Record<string, unknown>`：
那等于把 `sort` 拼错、`search` 结构写错这类错误全放给真机 400 去暴露。

两者都调同一个内部函数，差别只在 `search` 参数：

- 热门：`{ sort: "trendingScore", limit, search: { tags: ["gguf"] } }`
- 搜索：`{ sort: "trendingScore", limit, search: { tags: ["gguf"], query } }`

`additionalFields: ["trendingScore"]` 两者都带（见 §3 坑 2）。**不要 `createdAt`**：
`HfModelSummary` 里没有这个字段，卡片显示的是 `updatedAt`，多要一个字段等于白扩一次 expand。

`listModels` 是 async generator，内部循环到 `limit` 条即 `break`。**这是防御性上限，
不是必需的截断**：库在收到 `limit` 时自己就会 `totalToFetch--` 并提前 return，首页请求也按
`Math.min(limit, 500)` 限了量；`break` 只是不把上游的截断语义当成前提。

## 7. 缓存：进程内，不加表

热门榜缓存在模块级 `Map`，键为 `` `${endpoint ?? "official"}::${limit}` ``，TTL 30 分钟。
取远端失败且 Map 里有旧值时**回落旧值并标 `stale: true`**，语义照抄 `hf/repoFiles.ts`
（那份文件的头注释解释了为什么「失败不能把用户已有的数据弄没」）。

TTL 读 `PANEL_HF_TRENDING_TTL_MINUTES`，解析规则与 `lib/cache-freshness.ts` 的
`resolveTtlMs` 同构（非数字/负数回落默认、`0` = 永不过期），但**单位是分钟不是小时**，
因此在 `lib/hf-models.ts` 里单写一个 `resolveTrendingTtlMs(raw)`，不复用
`resolveTtlMs`——后者的单位写死在小时上，热门榜的自然量级是分钟，混用会让环境变量的
含义在两处不一致。新鲜度判定本身直接复用现成的 `isStale(fetchedAt, now, ttlMs)`。

**不建 SQLite 表，是刻意取舍**：热门榜是纯派生数据、12 条 JSON 不到 3KB、重启重取一秒。
代价是面板重启后榜单空一下——它是锦上添花，不是 `repo_files_cache` 那种「丢了用户就看不见
自己仓库文件」的数据，不值得为它加表加迁移。

**搜索结果不缓存**（查询空间无限），靠前端 400ms debounce + `AbortController` 压请求量。

## 8. 纯逻辑下沉 `src/lib/hf-models.ts`

vitest 是 node 环境、无 jsdom，可测判定一律下沉到这里：

```ts
export const HF_DISCOVER_LIMIT = 12;
export const OFFICIAL_HF_ENDPOINT = "https://huggingface.co";

/** listModels 返回体 → 视图模型；trendingScore 缺省映射为 null。
 *  入参按结构类型声明（见下方 ModelEntryWithExtras），不 import 库的
 *  `ModelEntry` / `ResolveModelAdditionalFields<T>`——本模块会被客户端组件
 *  间接 import，从这里牵进 @huggingface/hub 会把一个纯服务端库拖进浏览器 bundle */
export function toModelSummary(raw: ModelEntryWithExtras): HfModelSummary;

/** 单仓库外链：`${endpoint}/${repo}` */
export function hfRepoUrl(repo: string, endpoint: string): string;

/** 站内列表页外链（「更多」长按钮）：
 *  热门态 `${endpoint}/models?other=gguf&sort=trending`
 *  搜索态 `${endpoint}/models?search=<encode(q)>&other=gguf`
 *  搜索态刻意不带 sort——HF 站内搜索默认按相关度排，压成 trending 反而更差 */
export function hfListUrl(query: string, endpoint: string): string;

/** TTL 环境变量（分钟）→ 毫秒；见 §7 为何不复用 resolveTtlMs */
export function resolveTrendingTtlMs(raw: string | undefined): number;

/** 满屏判定：本地不翻页，返回条数够一屏就认为还有更多 */
export function hasMoreResults(count: number, limit: number): boolean;

/** 查询串 limit 解析：非整数 / <1 回落 HF_DISCOVER_LIMIT，>50 夹到 50 */
export function parseLimit(raw: string | null): number;
```

**`formatCount` 不放这里，放 `src/lib/format.ts`**（`1908396 → "1.9M"`、`4440 → "4.4k"`、
`886 → "886"`）：它是通用的计数格式化，与 HF 无关，而 `format.ts` 的文件头注释已把自己
定义为「展示格式化小工具（server / client 通用，无依赖纯函数）」，`formatSize` 就住在那里。
埋进 HF 专属模块会让下一个需要它的人找不到、再写一份。用例并入现成的 `lib/format.test.ts`。

`other=gguf` 而非 `library=gguf`：前者与 API 的 `filter=gguf` 同为标签筛选，口径一一对应，
面板列出的与点过去看到的是同一批（两者实测都 200，见 §3）。

## 9. 首页第三区

```
┌─────────────────────────────────────────────────────────────┐
│ HuggingFace 热门 · GGUF          [🔍 搜索模型…        ] [↻] │
├─────────────────────────────────────────────────────────────┤
│ ┌───────────────────────┐ ┌───────────────────────┐        │
│ │ Qwen3.8-27B-GGUF      │ │ Ternary-Bonsai-2-27B  │ …      │
│ │ unsloth      [已有档案] │ │ prism-ml              │        │
│ │ 🔥324  ♡4.4k  ↓1.9M   │ │ 🔥1.5k ♡1.6k  ↓1.9M   │        │
│ │ text-generation · 3天前│ │ text-generation · 5天前│        │
│ │          [↓ 下载]  [↗] │ │          [↓ 下载]  [↗] │        │
│ └───────────────────────┘ └───────────────────────┘        │
│                     （共 12 张，网格 2/3 列自适应）           │
├─────────────────────────────────────────────────────────────┤
│ │           在 HuggingFace 查看更多 →                    │  │
└─────────────────────────────────────────────────────────────┘
```

接在现有的 `<HomeRunning>`、`<HomeRepos>` 之后，是首页滚动容器里的第三块。

**两态共用一块区域**：搜索框有词时区标题变「搜索结果 · <词>」并出现清除按钮，清空即回
热门态。不新增路由，不在 URL 上落查询词——这块是首页的一个探索入口，不是可分享可回退的
独立页面；把词写进 URL 会让浏览器「后退」变成在首页内部翻搜索历史，与「后退应离开首页」
的直觉相悖。

`[↻]` 手动刷新绕过缓存（`?refresh=1`），语义与档案详情页的刷新按钮一致。

### 9.1 `[已有档案]` 徽标

该 repo 本地已建过仓库档案时，卡片右上标徽标，且 `[↓ 下载]` 换成 `[查看档案 →]` 直达
`/models/repos/<id>`。数据零额外开销：`page.tsx` 本就装配了 `profiles`，把
`{ repo, id }` 映射透传给客户端组件即可，不多查一次库。

热门榜里撞上自己已有的仓库是常事，不标会让人重复建档。

### 9.2 通栏「更多」按钮

`items.length >= HF_DISCOVER_LIMIT` 时，在网格下方给一条**通栏**（`w-full`）按钮，
`target="_blank" rel="noopener noreferrer"` 打开 `hfListUrl(query, endpoint)`。
不足 12 条则不渲染——结果没满一屏，说明 HF 那边也没有更多了。

热门态恒满 12 条，所以这条按钮在热门态实际上长驻，这是预期行为。

## 10. 下载弹层预填

`NewDownloadDialog` 新增 `defaultRepo?: string`。实现极轻：表单里
`const [repo, setRepo] = useState("")` 改为 `useState(defaultRepo ?? "")`。该表单本就靠
`key={generation}` 在每次打开时整体重挂载（见其头注释），预填天然生效，**不需要任何重置
逻辑，也不需要 effect**。

附带修一处交互毛刺：仓库探测当前只挂在 repo 输入框的 `onBlur` 上
（`new-download-dialog.tsx:326`），预填进去的值不会失焦、因而不会自动探测，用户得先点一下
输入框再点走才看得到量化分组。**`defaultRepo` 非空时，挂载后自动探测一次**，点开即见分组。

自动探测用 `useEffect(() => { if (defaultRepo) void probeRepo(); }, [])`——表单每次打开都是
全新实例，"挂载时跑一次"就是完整语义，不存在 open 变化要重跑的情况；写法与该文件里已有的
`repoDirs` 拉取 effect 同构。

## 11. 错误与降级

| 情形 | 表现 |
|---|---|
| 加载中 | 6 张骨架卡（`animate-pulse`），区标题与搜索框正常可用 |
| 失败 + 无缓存（502） | 一行中文原因（`mapHfError` 出品）+「重试」按钮 +「去设置配置镜像/代理 →」链接指 `/settings` |
| 失败 + 有旧缓存（200 stale） | 照常显示旧卡片，网格上方一行提示「显示的是 N 分钟前的缓存」+ 重试 |
| 搜索无结果 | 「没有匹配的 GGUF 仓库」+ 提示换个关键词；此时不渲染「更多」按钮 |
| 搜索请求被新输入取代 | `AbortController` 中止，静默丢弃，不弹错 |

`src/lib/hf-models.test.ts`：

- `hfRepoUrl` / `hfListUrl`：官方端点与镜像端点各一组；搜索词含空格与斜杠时的
  `encodeURIComponent`；搜索态不带 `sort`、热门态带 `sort=trending`。
- `formatCount`：`886` / `4440` / `1908396` / `0` / 恰好 `1000` 与 `1000000` 的边界。
- `resolveTrendingTtlMs`：默认值、`"0"` → `Infinity`、负数与非数字回落默认。
- `hasMoreResults`：`11/12` → false、`12/12` → true。

`src/server/hf/models.test.ts`（注入假 `listModels`，不打网络）：
- 首次取 → 落缓存，`fetchedAt` 非 0、`stale: false`。
- TTL 内再取 → 不调用注入的 `listModels`（断言调用次数为 1），返回同一批。
- TTL 外再取 → 重新调用，`fetchedAt` 更新。
- TTL 内带 `refresh: true` → 强制重新调用（断言调用次数递增），新值覆盖缓存。
- `refresh: true` 但远端抛错且有旧缓存 → 仍回落旧值 + `stale: true`，**旧缓存不被清空**
  （刷新失败不该把用户正看着的榜单弄没，与 `repoFiles.ts` 同款语义）。
- 远端抛 `HubApiError(429)` 且有旧缓存 → 返回旧 `items` + `stale: true` + 中文 error。
- 远端抛错且无缓存 → `items: []` + `error` 非空，交由 route 转 502。
- 搜索不写缓存：搜索后再取热门，热门缓存不被污染（键隔离）。
- `limit` 截断：假数据给 30 条，`limit: 12` 只返回 12 条。
