# 监控与日志

监控指标集中在概览页（`/`），日志页（`/logs`）只保留运行历史与容器日志两项排查手段，避免同一组数字在两处各显示一遍。

## 概览页：13 张读数 + 曲线合卡

概览页左列是监控合卡区，共 13 张卡，分四组：

| 分组 | 卡片 |
| --- | --- |
| 宿主机（6 张） | CPU 利用率、内存、负载、磁盘剩余、磁盘 IO（读/写）、网络收发（接收/发送） |
| GPU（2 张） | 显存、GPU 利用率 |
| 容器（2 张） | CPU（容器）、内存（容器） |
| 推理（3 张） | 生成速率、KV Cache、活跃槽位 |

每张卡是「卡头当前值 + 历史曲线」的合体（磁盘剩余例外，见下）。这两部分来自**两条节拍不同、来源不同的数据流**：

- **卡头大数字**：跟随页顶的刷新间隔选择器刷新（默认 5 秒，选择记在浏览器本地），取的是这一刻的实时读数——哪怕当前正看着 7 天档的历史曲线，卡头也不会显示某个更粗粒度里的旧值。
- **历史曲线**：跟随页顶的时间范围 Tabs（`30m` / `2h` / `24h` / `7d`）切换（见下节「历史数据能回溯多久」）。

磁盘剩余是唯一例外：变化太慢，折线看不出趋势，降级为只有卡头读数（配一个已用/剩余环形图），没有历史曲线也没有放大入口。

GPU 两卡与推理三卡的数据分别来自同一次探测，所以要么一起有数据、要么一起显示空——不会出现「利用率有数据，显存却空着」这种一半有一半没有的情况。宿主机与容器卡则彼此独立，缺 CPU 数据不代表磁盘 IO 也会跟着缺失。

## 多卡聚合口径

多张 GPU 时，显存、利用率、温度、功耗四项的合并方式不同，看数字前先确认是哪一种：

| 指标 | 聚合方式 | 是否进历史曲线 |
| --- | --- | --- |
| 显存占用 | 求和 | 是 |
| GPU 利用率 | 算术平均 | 是 |
| 温度 | 取各卡最高值 | 否（只在卡头副标展示） |
| 功耗 | 求和 | 否（只在卡头副标展示） |

温度取最高而非平均，是因为温度这个指标关心的是"有没有卡在过热边缘"——平均值会把一张 85℃ 一张 45℃ 的极端情况抹成看起来正常的 65℃。多卡时卡头副标会额外拼一句"{n} 卡合计"提示，单卡不显示（没有歧义）。

## CPU% 口径

容器 CPU% 与宿主机 CPU% 是两个不同口径的数字，取值范围也不同。

容器 CPU% 与 `docker stats` 口径一致，**按核数展开**：16 核机器满载显示的是 1600%，不是 100%。卡头副标「{核数} 核 · 满载 {核数×100}%」标出了这台机器的满载参考值。

宿主机 CPU% 是整机利用率，始终落在 0–100 之间（多核已经在系统层面被折算成一个整体利用率，不需要再乘核数）。

所以这两个数字不能直接比大小——容器卡显示 400%、宿主机卡显示 25%，在一台 16 核机器上说的是同一件事（用掉了 4 个核）。

## 历史数据能回溯多久

页面上可选的时间范围有四档：30 分钟、2 小时、24 小时、7 天。时间跨度越长，曲线的采样点越粗，这由底下三层存储决定：最近 2 小时是 5 秒一个点，再往前有一层 1 分钟的聚合保留 48 小时，更早的落到 15 分钟一个点、保留 14 天。

这三层是内部存储分层，不是可选项——面板会按你选的范围自动取当前能拿到的最细粒度，不需要手动挑。30 分钟与 2 小时两档走 5 秒粒度，24 小时与 7 天两档走 15 分钟粒度；1 分钟那一层只在 24 小时档、且时间落在 48 小时保留期内时被静默混进结果里，不会单独作为一个档位出现。

重启面板会丢掉最近两小时的 5 秒级细节，那一段曲线会变粗；48 小时和 14 天的历史存在磁盘上，不受重启影响。

## 宿主机磁盘 IO 与网络收发都依赖 `/proc` 挂载

CPU / 内存 / 负载 / 磁盘剩余这几项指标面板容器自己就能采到，但**磁盘 IO 速率和网络收发速率这两组指标都需要额外挂载宿主机的 `/proc`**（`docker-compose.yml` 里的 `/proc:/host/proc:ro`）。

没挂这一行时，这两组指标静默缺省（不报错、不影响其余指标），从旧版升级上来的部署要留意——这个挂载是容器级配置，`docker compose restart` 不会应用，需要 `docker compose up -d` 让它按需重建容器。

## GPU 监控前提

GPU 两张卡（显存、利用率）依赖面板容器能调用 `nvidia-smi`，也就是 `docker-compose.yml` 里的 `gpus: all`。没有这一行时两卡会隐藏，并在图表区顶部出现提示条；纯 CPU 部署下这是正常状态。

## 日志页：运行历史与容器日志

日志页（`/logs`）分两组：

- **历史**：每次模型启停记一行，列出模型、开始时间、时长、平均 tok/s、峰值显存。峰值显存展示的是**净增量**（峰值 − 启动前基线），不是启动后那一刻整卡的占用——本机常有别的旁路任务同时跑在同一张卡上，直接展示整卡峰值会让人误以为"这个模型吃了这么多显存"，减掉启动前的基线才是这次运行自己的净开销。
- **容器日志**：`llama.cpp` 容器的实时日志流，实时推送到页面，不需要手动刷新。

## Webhook 通知

下载完成、模型启停等事件可以推送到 Bark / Telegram / 企业微信或自定义接收端，配置入口在[设置页](./settings.md)的「监控与通知」组。

## 已知边界

生成速率采不到短于 5 秒采集间隔的生成——一次推理如果在 5 秒内就结束，采集心跳可能一次都没赶上，卡头和曲线会显示为空而不是 0，这不代表推理没有发生。
